Where Rust actually matters for an API service

I built the same API in Rust, Go and Python, with each ecosystem's production stack, and measured seven workloads on nine metrics. The honest answer is "it depends on the workload". Here is the dependence, with numbers.

November 2026 · 9 minute read · code and raw data

"Rust is faster than Python" is true and useless. The questions worth an evening are where, by how much, what it costs, and whether the thing your service does all day is one of the places where it matters.

So: the same contract, implemented three times. Rust with Axum on Tokio. Go with the standard library's net/http. Python with FastAPI on Uvicorn, uvloop, httptools and orjson, run both as ten workers (one per core) and as one worker so the cost of scaling Python stays visible. Seven endpoints, each isolating one thing an API spends time on: the framework floor, a lookup, a 200-item list, a write, pure CPU, pure I/O wait, and a realistic mix. A shared contract test that refuses to benchmark anything that behaves differently. Hypotheses written down before the first run.

Load from oha, 64 connections, 10 seconds per cell, a fresh process per scenario, on an Apple M5 with 10 cores. The load generator shares the machine, which understates every number equally. Read everything as relative.

The one chart

Read it by rows. The bottom two, where the request is waiting on something, are grey everywhere except the CPU and memory columns. The language does not decide how fast a waiting request goes. It decides what it costs while it waits.

Where Rust wins

CPU on the request path

On 5,000 rounds of SHA-256 per request, Rust served 23.7k requests a second. Go served 11.5k, ten-worker Python 3.2k, one-worker Python 979. That is 2× Go and 7× Python with every core lit.

Past saturation is where it gets interesting:

Rust missed the deadline on zero requests with a p99 of 145 ms. Go missed 0.2% at 698 ms. Ten-worker Python missed 2.1%, one-worker Python 63%. Go's median under overload (21 ms) beat Rust's (51 ms) while its p99 was five times worse: Go's scheduler serves some requests fast and lets others wait out the deadline, Tokio's work-stealing spreads the delay evenly. If you have an SLO, evenly is what you want.

Tail latency

On a lookup, Rust's p99 is 0.71 ms and 2.1× its median. Go's is 1.83 ms at 6×. Ten-worker Python's is 5.87 ms at 11×. Under CPU load Go's p99 opens to 24× its median; Rust's stays at 2×. If your SLO is written against p99, Rust is the only one of the three whose tail stays flat.

Density

Per 1,000 lookups, Rust spends 22 ms of CPU, Go 30, ten-worker Python 93. Idle memory is 9.9 MB, 13.5 MB and 710 MB. Across a fleet, that is the bill.

Where it does not

  • I/O-bound endpoints. On a 10 ms wait, all four land within 8% on throughput and within 1 ms on p99, and Rust is last: Tokio's sleep(10 ms) takes 12.3 ms on this Mac even with one connection, while Go and uvloop take 11.3. Rust buys you 2 to 4× less CPU and 2 to 50× less memory while you wait. It does not buy you speed.
  • Serialization. 1.2× Go, 1.6× tuned Python on a 200-item list.
  • Memory per connection. Holding 1,000 idle connections cost Rust 31.6 KB each, Go 23.2, Python 18.5. Hyper buffers the most. My hypothesis had the order backwards.

Two one-line changes

I kept the first run, with every framework at its defaults, in the repo on purpose.

FastAPI returning a dict runs its pure-Python jsonable_encoder over the response before orjson serializes it. On 200 items that was 1.7 ms of CPU per request and a 14× gap to Rust. Returning ORJSONResponse(...) directly took the gap to 1.6×.

Rust was slower than Go on hashing in the baseline: 8.4k against 14.7k. Go's crypto/sha256 uses the ARM SHA-2 instructions out of the box; Rust's sha2 crate defaults to software. Its asm feature tripled throughput with an identical digest. The language sets the ceiling; the library decides whether you reach it.

Things I did not expect

Ten-worker Python has no shared memory. The contract test found it before the benchmark did: an item created on one Uvicorn worker is a 404 on the other nine. Python's only route to all ten cores is ten processes, which means ten copies of every in-memory structure and no shared state without Redis or a database round-trip that Rust and Go do not need for the same feature. This is the biggest practical difference in the study and it is architectural, not a benchmark number.

  • Nobody has a latency hangover. After a 5-second spike the first probe was back to pre-spike latency for all four. Memory is different: Rust and Python kept 100% of the spike's growth after 10 s idle, Go gave back 28%.
  • Python's per-request CPU is close to Go's. One worker spends 30 ms per 1,000 health checks; Go 28; Rust 21. uvloop, httptools and orjson are C. The expense is scaling: ten workers cost 78 ms per 1,000 because ten processes contend for ten cores.
  • Same contract, different error shapes. A non-numeric id is a plain-text 400 from Axum, a JSON 400 from Go because I wrote it, and a 422 with a Pydantic error array from FastAPI. Go is the only one where every byte of the error surface is yours.

What it costs

Rust and Go took the same number of lines, 177 and 182; Python 93. Rust ships 93 crates, Go zero, Python 21 packages. Clean build: 13.7 s Rust, 3.2 s Go. Cold start: 12 ms for both, 170 ms for one Python worker, 417 ms for ten. Go reaches within 10 to 25% of Rust on everything except CPU-bound work and tail latency, with zero dependencies and a 3-second build. It is the honest competitor here.

So what should you pick

  • You compute on the request path: Rust. 2× Go, 7× Python, and the only one that met the deadline for every request under overload.
  • Your SLO is on p99: Rust. The only tail that stays near 2× its median.
  • You mostly wait on a database: the language does not decide your latency. Pick for the team, then pay the memory and CPU bill: about 2× for Go and 50× for ten-worker Python, relative to Rust.
  • You need shared in-memory state across cores: Rust or Go. Python needs Redis for what the other two get from a mutex.
  • You want most of Rust's density without its dependency graph: Go.

Caveats

One machine, load generator on the same cores, 10-second windows, macOS rather than Linux, an in-memory store instead of a database. The numbers here are medians across four full runs; the spread is in the repo's report. Phase 2 is the same contract on PostgreSQL, where driver and pool quality take over and the gaps should narrow again.
